> [!Note] 关键问题：考虑到崩溃，如何更新磁盘
> 系统可能在任何两次写入之间崩溃或断电，因此磁盘上状态可能仅部分地更新。崩溃后，系统启动并且希望再次挂载文件系统。
> 鉴于崩溃可能发生在任何时间点，如何确保文件系统将硬盘上的映像保持在合理的状态？


# One detailed example
向文件追加内容时，要向它添加一个新数据块，因此必须更新 3 个磁盘上的结构：
- `inode`：必须指向新块，并且由于追加而具有更大的大小
- 新数据块 `Db`
- 新版本的数据为徒 `B[v2]` 表示新数据块已经分配

实现这种转变必须执行 3 次单独写入。可参考 [[OS-lecture-26 文件系统实现和崩溃一致性#乱序执行：后果]]

所以对于这 3 个写入，每个都可能失败（0）或者成功（1），共有 `8` 种可能。
- 都成功，和都失败，比较平凡，不考虑
- 剩下的很好玩！

每次写入可能失败 (0) 或成功 (1)，共 8 种结果：

| B   | Db  | Inode | 结果分析                                                                            |
| --- | --- | ----- | ------------------------------------------------------------------------------- |
| 0   | 0   | 0     | **全失败** — 无变化，一致但操作未生效                                                          |
| 0   | 0   | 1     | **仅 inode** — inode 指向未分配块且无数据 → 文件读到垃圾数据                                       |
| 0   | 1   | 0     | **仅数据块** — 数据写了但未标记分配、inode 未指向 → 数据孤立，完全丢失                                     |
| 0   | 1   | 1     | **数据+inode** — 数据已写入且 inode 已更新，但位图仍标记块为空闲 → 文件系统认为块可用，未来可能覆盖该块（**最严重**，导致数据损坏） |
| 1   | 0   | 0     | **仅位图** — 块标记已分配但无数据、inode 未指向 → 空间泄漏                                           |
| 1   | 0   | 1     | **位图+inode** — 块标记已分配且 inode 更新，但无实际数据 → 文件读到垃圾/旧数据（_journaling 中称为 "gap" 问题_）  |
| 1   | 1   | 0     | **位图+数据** — 数据写入且块已标记，但 inode 未更新 → 数据已存但文件看不到，空间泄漏（space leaking）              |
| 1   | 1   | 1     | **全成功** — 一致的正确状态                                                               |

**关键观察**：

- (000) 和 (111) 是平凡情况
- **(011) 数据+inode** 是最危险的 — 位图未更新意味着该块可能被复用，导致文件数据静默损坏
- **(101) 位图+inode** 是经典的 "gap" 场景 — 数据块未写入但 inode 已指向它，文件会读到磁盘上的旧内容
